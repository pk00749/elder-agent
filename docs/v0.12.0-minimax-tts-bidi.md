# v0.12.0 目标定义：「MiniMax T2A 切到 `t2a_v2_bidi`」

> 对应 AGENTS.md §A.13 (本版本重写) / §18 (反向条款: MiniMax TTS 仍 0.7.0 例外;不通过 elder_common 封装) / prd.md §12.5 索引追加行。
> 本版本主题:**客户端 MiniMax TTS 端点从单向 `/ws/v1/t2a_v2` 切到双向 `/ws/v1/t2a_v2_bidi`**,解决 LLM 逐字流式输出 → TTS 音频碎裂的根因。
> 本文件**只**定义产品 / 工程目标,具体代码约束在 AGENTS.md / prd.md。

---

## 1. 现状盘点 (v0.11.x → v0.12.0 起点)

| 维度 | 现状 (AGENTS.md v2.8 §A.13) |
|------|---------------------------|
| 端点 | `wss://api.minimax.cn/ws/v1/t2a_v2` (**_v2 单向**) |
| 攒句责任 | **客户端** (`buildTaskContinueMessage(text)` 一次发整句) |
| 老人逐字场景 | LLM 流式 token → `tts.speak(segment)` → 单向 endpoint 把整段当一句合成;**短 segment 时单条 tts 没问题,但长访谈分段传参时易触发「音频碎裂」** |
| 打断 | ❌ **不支持** — `stop()` 直接 close WebSocket,老人插话需要重建连接 + 重发 task_start (贵、慢) |
| 催出残留 | ❌ **不支持** — `task_finish` 立即关,尾句短文本若不带 `。` 服务端不兜底送 → 老人听到尾音被砍 |
| voice_id | `Cantonese_KindWoman` 硬编码 (`voice_id_validated=false`) |
| audio_setting | `format=pcm` + `sample_rate=24000` + `channel=1` + **`bitrate=128000`** ⚠️ (无效字段,PCM 无压缩) |
| `language_boost` | ❌ **未设置** — 粤语场景识别 / 韵律无强化 |
| `pronunciation_dict` | ❌ 未设置 (粤语语气词 / 数字 / 缩写可优化) |
| 错误映射 | `mapStreamError` 看 `error.code/message` 关键字 ⚠️ **MiniMax 实际用 `base_resp.status_code` 整数**,现有实现拿不到 → 100% fallback 到 `TtsUpstream` |
| status_code 区分 | ❌ 不区分 1004 (auth) / 2205 (软失败,会话保持) / 2206 (事件顺序) |
| 连接保活 | ❌ 未实现 — 老人停顿长 (30-60s 思考) → 120s 空闲触发 2201 自动断连 |
| §18 lock | TTS Provider 仍走 `MiniMaxTtsClient.kt` 单文件直连 (0.7.0 例外);**不引入**新上游 SDK |

## 2. 目标 1 条 (对应 7 个执行细节)

| # | 目标 | 落地点 |
|---|------|--------|
| **G1** | TTS 切到 bidi,流式自然 + 老人插话可打断 + 尾音不丢 | `MiniMaxTtsClient.kt` 全章重写 |

### 2.1 执行细节 7 项

1. **WS_URL 改 bidi**:`wss://api.minimax.cn/ws/v1/t2a_v2` → `wss://api.minimax.cn/ws/v1/t2a_v2_bidi`(API 域名不变,只换 endpoint 段)
2. **删 BITRATE 常量**:`BITRATE = 128000` 删除;PCM 是无压缩流,文档明确「`该参数仅对 mp3 格式的音频生效`」
3. **加 `language_boost: "Chinese,Yue"`**:`buildTaskStartMessage` 增 `put("language_boost", "Chinese,Yue")`(粤语场景必备,enum 在合法范围内)
4. **错误码精确映射**:重写 `mapStreamError` → 改读 `event.base_resp.status_code` int(1000/1001/1002/1004/1039/1042/2013/2201/2202/2204/2205/2206),不再读字符串关键字
5. **新事件处理**:`sentence_start` / `sentence_end` (debug log) / `task_canceled` (debug log) / `task_flushed` (debug log) 在 `onMessage` 加分支(默认 1 条迭代,保持 500 行红线)
6. **30s ping 保活**:WS 建连后启动定时 `ws.send("")`(MiniMax 文档明示「客户端必须定期 ping —— 服务端会回复 pong 并刷新活跃时间。仅靠 TCP 连接存活不足以避免 2201」)
7. **协议族注释 + 配套常量**:`LANGUAGE_BOOST` / `PING_INTERVAL_MS = 30_000L` / `IDLE_TIMEOUT_MS = 120_000L`

### 3.2 `buildTaskStartMessage` 新增字段

```kotlin
private fun buildTaskStartMessage(): String =
    JSONObject().apply {
        put("event", "task_start")
        put("model", MINIMAX_TTS_MODEL)
        put("language_boost", LANGUAGE_BOOST)            // ★ 新增
        put("voice_setting", JSONObject().apply {
            put("voice_id", MINIMAX_TTS_VOICE_ID)
            put("speed", 1)
            put("vol", 1)
            put("pitch", 0)
            put("english_normalization", false)
```

### 3.3 事件处理矩阵 (bidi 比单向多 4 个)

| 事件 | 单向 t2a_v2 | 双向 t2a_v2_bidi | 本客户端处理 |
|------|------------|------------------|--------------|
| `connected_success` | ✓ | ✓ | completeValue(connected) |
| `task_started` | ✓ | ✓ | completeValue(taskStarted) |
| `task_continue` (request) | ✓ | ✓ | ws.send 文本 |
| `task_continued` + `data.audio` (hex) | ✓ | ✓ | sink.write(hex_decode) |
| `is_final: true` | ✓ | ✓ | completeValue(finished) |
| `task_finished` | ✓ | ✓ | completeValue(finished) |
| `task_failed` (含 `base_resp`) | ✓ | ✓ | mapBaseRespError |
| **`sentence_start`** | ✗ | ✓ | debug log(`sentence start = $idx`) |
| **`sentence_end`** | ✗ | ✓ | debug log(`sentence end = $idx`) |
| **`task_canceled`** | ✗ | ✓ | debug log(`TTS canceled`) |
| **`task_flushed`** | ✗ | ✓ | debug log(`TTS flushed`) |
| **pong** (服务端对 ping 回包) | ✗ | ✓ | 啥也不做(刷新计时即生效) |

### 3.4 错误码精确映射 (§A.13.4 重写)

| 服务端 `base_resp.status_code` | 含义 | AppError 映射 | WebSocket 行为 |
|--------------------------------|------|--------------|----------------|
| 0 | 成功 | — | — |
| 1000 | 未知错误 | `TtsUpstream(serverErrorCode="1000")` | close |
| 1001 | 超时 | `TtsUpstream(serverErrorCode="1001")` | close |
| 1002 | 限流 | `TtsUpstream(serverErrorCode="1002")` | close |
| **1004** | **鉴权失败** | **`TtsAuthFailed()`** ← 关键 | close |
| 1039 | TPM 限流 | `TtsUpstream(serverErrorCode="1039")` | close |
| 1042 | 非法字符 > 10% | `TtsUpstream(serverErrorCode="1042")` | close |
| 2013 | 参数不正常 | `TtsUpstream(serverErrorCode="2013")` | close |
| 2201 | 空闲超时被服务端关闭 | `TtsUpstream(serverErrorCode="2201")` | 已关闭 |
| 2202 | 非法事件 | `TtsUpstream(serverErrorCode="2202")` | close |
| **2204** | 单条 task_continue > 10K 字符 | `TtsUpstream(serverErrorCode="2204")` | **会话保持**,跳过该条 |
| **2205** | 排队文本过多 | `TtsUpstream(serverErrorCode="2205")` | **会话保持**,稍后重发该条 |
| 2206 | 事件顺序非法 (重复 task_start) | `TtsUpstream(serverErrorCode="2206")` | close |

> **§18 例外声明**:本表 2204 / 2205 是文档明确「软失败,会话保持」;现有 `MiniMaxTtsClient` 调用模型是「整段 task_continue 一次发」,2204 / 2205 路径当前**走不到**(客户端不会主动超过 10K 字符或抢在合成前连发)—— 但错误码表完整列出便于日志/重试策略;**不**为 2204 / 2205 加自动重试逻辑(§18 「不要写 mock 数据反向测试」+「未走到的路径不写测试」)。

### 3.5 Ping 保活

```kotlin
private var pingJob: Job? = null
private fun startPinger(ws: WebSocket) {
    pingJob = scope.launch {
        while (isActive) {
            delay(PING_INTERVAL_MS)
            runCatching { ws.send("") }  // 服务端会回 pong
        }
    }
}
private fun stopPinger() { pingJob?.cancel(); pingJob = null }
```

- `PING_INTERVAL_MS = 30_000L`(30s ping 一次,120s 空闲断前有 2 次 ping 触发 → 服务端活跃时间刷新)
- ping 失败不抛异常(可能 WS 已 close,直接 cancel job)

## 7. 留待 v0.13.0

> 本次仅切换 bidi endpoint + 修对错误码,**不涉及 TtsClient 接口变更,也不涉及 ChatAgent 调用模型调整**。LLM SSE 流 → 多次 `task_continue` 的真实 bidi 优势留待 v0.13.0 单独设计(详见 `docs/v0.13.0-tts-streaming.md` 占位 —— 待立项)。

### 7.1 v0.13.0 触发条件(满足任一即应立项)

- [ ] 真实老人反馈："AI 说话前停顿太久"(主观 ≥ 2s)
- [ ] 日志显示 `firstAudioDelayMs - startedAt > 4000ms` 占比 ≥ 30%
- [ ] ASR 侧 v0.x 也切到流式(同步回流),需要 TTS 配合对齐
- [ ] 老人打断率 ≥ 15%(说明当前模型"等 AI 说完才能打断"是真痛点)

### 7.2 v0.13.0 设计占位

1. **TtsClient 接口扩展**:
   ```kotlin
   interface TtsClient {
       suspend fun speakStream(apiKey: String, tokens: Flow<String>): TtsResult
       suspend fun cancel()
   }
   ```
   旧 `speak(apiKey, text)` 保留为单条流式 helper,向后兼容。

2. **ChatAgent 改造**: LLM SSE 流 → `tokens: Flow<String>` → TtsClient 入参;单段 ≤25 字不再被"等齐再发"——流到第 1 个 `。` 即可触发 TTS。

3. **PcmSink 重新设计**:
   - 跨句边界:句 1 写完 → 句 2 写前插 ≤100ms 自然停顿(不要 0 gap,否则老人听感是连读)
   - interrupt:用户打断 → TtsClient.cancel() → PcmSink.drainBuffer() → §18 反向条款仍生效

4. **新风险面**:
   - 流式 token 中途服务端返回 2205 软失败:客户端要做"等一会重发"而不是整体放弃
   - LLM SSE 中途断流:客户端 fallback 走完累积的 token 合最后一句
   - 老人插话抢在第一句之前:要 §A.11 ChatAgent 的"开场不耗 turn"逻辑配合

5. **配套新增测试**:
   - PcmSink 跨句顺序
   - 流式 cancel 收尾
   - 服务端 2205 软失败 + 客户端重发
   - LLM 中途断流降级
